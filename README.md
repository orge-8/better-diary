# better-diary

让麦麦每晚写一篇真正像「自己写的」睡前日记。

对比 [bockegai/diary_plugin](https://github.com/bockegai/diary_plugin) 的核心改进：

| 问题（旧插件） | better-diary 的做法 |
|---|---|
| 50k 时间线一次性进 prompt，模型按时间顺序线性复述聊天记录 | **两阶段生成**：阶段一按块提取「值得写的事」并打分，阶段二只喂 top N 精选事件 |
| 「不要写成流水账」和「回忆到现在为止的对话」自相矛盾 | 素材已精选，prompt 只需专注成文；明确「最多写 N 件、没劲就写短」 |
| 日记是转述，没有记忆点 | **强制用「」引用聊天原话**，至少一处 |
| 字数超了靠 `smart_truncate` 硬砍，句子断在半截 | 字数软控制（模型侧遵守 `word_target ± word_tolerance`，默认 350 ± 150），永不硬截断 |
| 天气靠关键词计数猜 | 天气由模型随文生成，贴合当天氛围；**模型自己写的天气会被保留**（只规范化标点，不覆盖成默认值） |
| AI 腔重（"真是充实的一天"式结尾） | 显式禁令清单：禁总结升华、禁"我意识到"、禁排比、禁连续感叹号 |

## 安装

1. 把 `better-diary/` 整个目录放进 MaiBot 的 `plugins/` 下
2. **升级 / 换版本时，务必先删掉插件目录里的 `config.toml`**（重要，见下方「升级后插件加载失败」）
3. **配置取材范围**：`[diary].target_chats = ["group:群号"]`（v1.3.5 起默认 `filter_mode = "whitelist"`，
   不填就**不生成日记**；想收录全库须显式写 `filter_mode = "all"`，先读「数据流向与隐私」）
4. **配置 `[security].admin_ids`**（v1.3.4 起权限默认关闭，不填就没人能用命令，见「命令」一节）
5. **httpx 仅「发布到QQ空间」时按需使用**（manifest 已声明该依赖）：
   - 想要空间发布 → 在主程序虚拟环境里 `pip install httpx`；
   - 不装也能跑：插件照常加载，日记正常生成并**存档**（`/日记查看` 可看正文），
     仅发布步骤会提示缺少 httpx。此时建议把 `[qzone].enabled` 设为 `false`。
6. 改完 `capabilities` 后需**完整重启 MaiBot**（manifest 在加载前校验，热重载不生效）
7. Runner 会自动生成 `config.toml`，按需修改

> ⚠️ **只替换 `.py` 文件是不够的。** `config.toml` 由 Runner 生成、存放在插件目录内，
> 换版本时它会**原样留在那里**。请整个目录替换，或确认替换后不残留旧 `config.toml`。
> （这正是 better-diary 连续三轮「本地全绿、真机报插件初始化失败」的真正成因。）

**日记成品只发布到 QQ 空间**，聊天里只回报执行状态；想回看正文用 `/日记查看`。

## ⚠️ 数据流向与隐私（默认配置下务必先读这一节）

这插件会**读聊天记录**、**调模型**、并把成品**发到公开的 QQ 空间**。默认设置下的实际数据流是：

| 环节 | 默认行为 | 可控项 |
|---|---|---|
| **取材范围** | `[diary].filter_mode = "whitelist"`（v1.3.5 起）—— **只取 `target_chats` 里显式指定的会话**；没填就**什么都不抓、直接不生成**。收录全库（跨群+私聊）必须显式写 `filter_mode = "all"` | `target_chats = ["group:群号", "private:QQ号"]` 逐条指定；`"all"` 是显式选项、不再是默认 |
| **送给谁** | 时间线（含昵称与聊天文本）经宿主 `llm.generate` 送给**你配置的模型 Provider** | 走宿主模型配置，插件不直连任何第三方 |
| **落盘什么** | `ctx.paths.data_dir` 下的 `diaries.json`（成品 + 选材事件含**逐字原话** + META）、`continuity.json`、`cookies.json`（登录态，0600） | 不采集用户 ID/群号进 prompt；无上传接口 |
| **给别的插件什么**（v1.4.4） | 只读接口 `get_day_digest`：把**选材事件（含逐字原话）+ META + 跨天连续性**交给**主动来调的**插件；**不含日记正文**。不主动推送 | 想彻底不给就别装会调它的插件；本插件无法单方面关闭（见「给其它插件的只读接口」一节） |
| **公开发布** | 当天的日记正文发到**公开可见**的 QQ 空间说说 | `[qzone].enabled = false` 只存档不发布；补写/历史日期一律不发布 |
| **谁能触发** | fail-closed：`admin_ids` 留空时**谁都不能**（只放行 bot 控制台本机操作） | `[security].admin_ids` / `allow_all_users` |

**两条都不再默认放开**：权限闸管「**谁能触发**」（v1.3.4 起 fail-closed），取材范围管「**默认收多少料**」
（v1.3.5 起默认 `whitelist`）。两者都收紧是有意的 —— 日记会发到**公开**空间，一旦默认把
A 的私聊内容写进去，B 的群成员也能看到（正文还会按要求引用聊天原话）。
如果你确实要收录全库，写 `filter_mode = "all"` 时请知悉这个后果。

顺带明确：`/日记查看`、`/日记来源`、`/问日记`、`/那年今日` 会把上述素材与逐字原话**发到命令所在的会话里**，
所以它们和 `/日记` 共用同一道管理员闸（v1.3.4 起），非管理员静默忽略。

## 给其它插件的只读接口（v1.4.4）

插件暴露了一个**只读**的 `@API`，供别的插件了解「这几天聊了什么」（例如生活模拟类插件
把她推演用的「近期经历」接上真实聊天）：

```python
digest = await self.ctx.api.call(
    "org.orge-8.better-diary.get_day_digest", version="1", days=2
)
```

| 参数 | 说明 |
|---|---|
| `date` | 留空 = 存档里最新的一天；给定日期则从那天起往回取（非法日期按留空处理） |
| `days` | 最多取几天（1~30，越界会被夹取） |

返回（`schema_version = 1`）：

```json
{
  "schema_version": 1,
  "count": 1,
  "days": [{
    "date": "2026-09-28",
    "generated_at": "2026-09-28 23:41:02",
    "material_mode": "events",
    "items": [{"event_id": "ev_…", "who": "阿岚", "what": "说起她换了个新键盘", "quote": "这个轴体声音太大了"}],
    "meta": {"topics": [], "people": [], "projects": [], "unresolved": []}
  }],
  "continuity": {"previous_summary": "…", "important_events": [], "ongoing_projects": [],
                 "ongoing_topics": [], "unresolved_items": [], "updated_at": "…"},
  "reason": ""
}
```

**三条边界**：

- **只读**：不生成日记、不调模型、不写盘、不改任何状态；坏存档由自己记 ERROR 并回退 `.bak`。
- **不给日记正文**：`content`、`published_at`、`model_date_line`、`word_count` 都不在返回里。
  给出去的就是 `/日记来源` 已经在聊天里展示过的那些字段（选材事件 + META + 跨天连续性）。
- **取不到也不抛**：没存档 / 参数乱写 / 目录读不到，一律返回 `days: []` + `reason`，由调用方决定降级。

`items` 至多 `[diary] max_events` 条（默认 3）——也就是「当天最值得写的那几件」，天然不会刷屏。
选材降级那天（`material_mode == "timeline_tail"`）`items` 会是空的，但 `meta` 里的话题/人物仍在。

## 命令

| 命令 | 权限 | 说明 |
|---|---|---|
| `/日记` | 管理员 | 生成今天的日记并发布到QQ空间 |
| `/日记 2026-09-26` | 管理员 | 补写指定日期的日记（**只存档不发布**；未来日期直接拦下） |
| `/日记 2026-09-26 重写` | 管理员 | 覆盖重写该日期已有的日记。**注意**：当天的日记会被**重新发布**一条到QQ空间（这是显式意图；不加「重写」则默认跳过，既不重调模型也不重发） |
| `/日记查看 [日期]` | 管理员 | 在聊天里回看已存档的日记 |
| `/日记来源 [日期]` | 管理员 | 查看某天日记依据了哪些选材事件（证据链） |
| `/问日记 <关键词>` | 管理员 | 搜历史日记，多个词空格隔开、都要命中（**本地检索，不调用模型**） |
| `/那年今日` | 管理员 | 往年同月同日的日记（本地检索） |
| `/日记帮助` | 管理员 | 用法说明 |

**权限默认关闭（v1.3.4 起 fail-closed）**：

- 管理员由 `[security].admin_ids` 控制，兼容 `"123456789"` 与 `"qq:123456789"` 写法；
  **留空 = 谁都不放行**（只有宿主 bot_console 的本机操作者可用），不再是「留空时全部放行」。
- 理由：**所有命令都在读取材范围内的聊天素材**，`/日记` 还会把结果发布到**公开**的 QQ 空间，
  默认「谁都能触发」风险过高。
  只读命令（`/日记查看` `/问日记` `/那年今日` `/日记来源`）与 `/日记` 受**同一道闸**保护 ——
  否则任意群成员都能把含私聊原话的日记拉进本群公开阅读。
- 确实想让所有人可用：`[security].allow_all_users = true`（显式开关，风险自负）。
- 唯一不受 `admin_ids` 约束的旁路是宿主注入的 `is_local_operator`（bot 控制台本机操作），
  插件按**严格布尔**判定（只认 `True` 与 `"true"/"1"/"yes"/"on"`，`"false"`/`"0"`/`0` 都不放行）；
  用户可控的命令参数（正则捕获组）从不并入权限 kwargs，无法从聊天消息伪造这个键。
- 非管理员使用时**静默忽略**（不回复任何消息，只留一行日志）。
- `[security].command_cooldown_seconds`（默认 300）限制同一会话两次 `/日记` 的最小间隔，
  防止刷屏式触发 LLM 调用与公开发布。`0` = 关闭。
  **判定顺序**：先看「该日期是否已有日记」（给出「要重写就加 重写」的可执行提示），
  再看冷却 —— 否则冷却期内连文档推荐的 `重写` 都会被挡住，用户只能干等。

## 配置

```toml
[plugin]
enabled = true
config_version = "1.0.0"

[diary]
word_target = 350          # 日记正文字数目标（只是最舒服的长度，不是硬指标）
word_tolerance = 150       # 目标字数上下浮动，区间 = 200~500。放宽一点，模型写长了不必回头删
max_events = 3             # 最多写几件事
min_messages = 20          # 当天消息少于此数不生成
filter_mode = "whitelist"  # whitelist（默认，只取 target_chats）/ all（全库，跨群+私聊）/ blacklist
target_chats = ["group:123456"]  # 取材范围。whitelist 下**必须填**，留空则不生成日记
persona_override = ""      # 留空读取主程序 personality.personality
style_extra = ""           # 追加风格要求，如 "多用叠词"

[schedule]
enabled = true
time = "23:30"             # 每天生成时间（Host 本地时区）
notify_chats = []          # 定时发布后通知哪些聊天，如 ["group:123456"]；留空不发通知
catch_up_enabled = true    # 补写缺档：插件启动与次日兜底各扫一次，给没有日记的日期补写（只存档、不发布）
catch_up_days = 3          # 补写最多往前看几天（不含今天）。这个上界同时充当「生效日」，绝不追溯更早的空档
fallback_time = "04:10"    # 次日凌晨的兜底补写时刻；留空或与 time 相同则关闭兜底
wait_silent_minutes = 0    # 静默阈值：到点时若最近 N 分钟内还有新消息，就等人停下再写。0 = 关闭（到点直接写）
retry_interval_minutes = 30  # 还没静默时，每隔多少分钟再看一次
max_wait_hours = 3         # 最多等多久；等满就照常生成（不丢天优先）。0 = 第一次发现没静默就直接写
catch_up_budget_minutes = 0  # 一轮补跑的总时长上限（分钟）。0 = 不限制；网络全崩时可设个上限避免长时间占用

[qzone]
enabled = true             # 日记生成后发布到QQ空间
auto_cookie = true         # 自动获取 cookie：adapter API → NapCat HTTP → 手动兜底，逐级降级
refresh_interval_min = 60  # 自动取 cookie 的节流间隔（分钟）
napcat_http_host = "127.0.0.1"  # NapCat HTTP 服务器地址（1.3.0+ 无 adapter 时的主要来源）
napcat_http_port = "3000"       # NapCat HTTP 服务器端口
napcat_http_token = ""          # NapCat HTTP 服务器 token（未设鉴权留空）
uin = ""                   # 手动兜底 cookie 的 QQ 号（自动获取失败时才用到）
p_skey = ""                # 手动兜底 cookie 的 p_skey（可留空）
skey = ""                  # 手动兜底 cookie 的 skey（可留空）
timeout_seconds = 20       # 发布请求超时（秒）

[llm]
task_name = "utils"        # Host 模型任务名
temperature = 0.8          # 成文温度
extract_temperature = 0.2  # 选材温度（低温保 JSON 稳定）
timeout_seconds = 180      # 单次 LLM 超时（已显式覆盖 RPC 30s 默认值）
write_retry = 1            # 成文遇**超时**类失败时额外重试几次。0 = 不重试
retry_backoff_seconds = 20 # 成文重试前的等待秒数（给网络抖动一点恢复时间）

[security]
admin_ids = ["123456789"]  # 管理员 QQ；留空 = 谁都不放行（fail-closed）
allow_all_users = false    # 高级开关：true = 允许所有人使用命令（含公开发布），默认关闭
command_cooldown_seconds = 300  # 同一会话两次 /日记 的最小间隔（秒），0 = 关闭
```

**关于列表型配置项**：`target_chats` / `notify_chats` / `admin_ids` 标准写法是数组
（`["group:123456"]`），但**写成字符串也能用**——单个值直接写 `"group:123456"`，
多个值用逗号分隔 `"group:111,group:222"`（中英文逗号都认）。v1.2.3 起做了前置归一化，
避免手写格式不对导致整个插件注册失败。

**`target_chats` 的三种写法**（v1.3.6 起明确支持第三种）：

| 写法 | 行为 |
|---|---|
| `"group:群号"` | 调宿主 `chat.get_stream_by_group_id` 解析成聊天流 ID |
| `"private:QQ号"` | 调宿主 `chat.get_stream_by_user_id` 解析 |
| `"05b32a99…"`（**裸聊天流 ID**） | **原样使用，不做任何解析** —— 解析环节出问题时用这个绕过。ID 从日志里的 `聊天流ID：xxxx` 复制，或 WebUI 的会话列表里取 |

> 三种写法都受 `filter_mode = "whitelist"` 约束；`all` 模式下 `target_chats` 只被 `blacklist` 之外的用途忽略，
> 别指望它在 `all` 模式下起过滤作用（这正是 v1.3.5 升级踩坑的根源）。

## 工作原理

```
当天消息（get_by_time / get_by_time_in_chat，按 filter_mode 取白名单会话）
   │
   ▼
时间线构建（时段标记 + bot 消息标注为"我"）
   │
   ▼  分块（chunk_chars，最多 max_chunks 块，并发选材）
阶段一：每块提取 0-4 件"值得写的事"（who/what/quote/score JSON）
   │  合并 → 按 score 排序 → 去重 → 取 top max_events
   ▼
阶段二：基于精选事件写日记
   首行「2026年9月26日 星期六，晴。」+ 正文（引用原话 + 反 AI 腔规则）
   │
   ▼
存档 data/diaries.json（原子写）→ 发布到QQ空间（说说，纯文本）
```

- **QQ空间发布**：cookie **三级来源逐级降级**——① napcat-adapter API（1.2.x 可用，1.3.0 起 adapter 不兼容自然跳过）→ ② NapCat HTTP 服务器的 `get_cookies`（OneBot 标准动作，与 MaiBot 版本无关，需在 NapCat WebUI 网络配置里开启一个 HTTP Server）→ ③ `[qzone]` 手动填的 cookie 兜底。内存缓存 + 节流 + `data_dir/cookies.json` 原子落盘（权限 0600）；登录态失效（code -3000 等）自动强制重取一次再试。发布接口 `emotion_cgi_publish_v6`，g_tk 用 p_skey 走 5381 算法。
- **发布前语义闸（v1.2.6）**：日记成品是**公开可见**的，所以成文结果必须过一道闸——**模型拒答**（如「抱歉，作为一个人工智能…」）、**空输出**、**残句**（正文不足 20 字）一律判失败，**本日不存档也不发布**，只在日志里留一行 `日记成文不可用（…）`。判定只认强标记，正常日记里的「我一时无法理解他为什么这么说」不会被误伤。
- **外发请求不跟随跳转（v1.2.6）**：发布请求携带登录态 cookie，因此显式 `follow_redirects=False`，并把 cookie 以**域限定**（`user.qzone.qq.com`）写入 client jar。收到 3xx 直接判失败并只回显跳转目标主机名——从结构上杜绝「跳转把凭据带去别的域」。
- **本地零 LLM 检索（v1.3.0）**：`/问日记 <关键词>` 与 `/那年今日` 是**纯本地检索**——
  字符串匹配 + 日期比对，不调用模型、零额外成本。检索范围 = 日期 + 正文 + 选材事件
  （who/what/quote）+ META 标签；多个关键词用空格隔开，**全部命中**才算（AND，压常见词噪音）。
  结果摘要优先取「命中关键词的那件事」，其次第一条事件，最后 META 话题 / 正文开头；
  按日期倒序最多 5 条。`/那年今日` 只看**年份更早**的同月同日（今年的今天不算「那年」）。
  借鉴 diary_writer 的 `retrieval.py` —— 这正是 v1.2.8 证据链的第一次兑现：
  没有结构化的 events / meta，这两个命令做不出来。
- **选材降级**：阶段一失败或选出 0 件时，自动降级用当天时间线末尾 4000 字作素材，流程不中断。
- **RPC 超时**：LLM 调用显式带 `timeout_ms`，绕开 `cap.call` 默认 30 秒限制。
- **存档**：`ctx.paths.data_dir/diaries.json`，临时文件 + `replace` 原子写；读取坏文件当空处理。
- **日志脱敏（v1.2.6 起，v1.3.4 收口）**：cookie 相关异常、adapter 返回的 error 字段、
  发布异常文本与空间响应体，在写日志/回消息前统一过 `redact_secrets`（`p_skey=<redacted>`、
  `g_tk=<redacted>`），避免登录态进日志文件。v1.3.4 补齐了三处缺口：plugin.py 侧发布异常、
  空间失败响应体不再回显、引用体检告警不再打印聊天逐字原话（改打事件 ID 与条数，
  要看原文用 `/日记来源`）。

- **关于模型侧超时（不是插件 bug，但会让人觉得"日记又没成"）**：真机日志里大量
  `任务 'plugin.org.orge-8.better-diary' 的模型 '…' 遇到错误: 网络连接超时 / 最大超时时间：30s`
  来自 **Host 侧模型 Provider**，不是插件。插件侧 `[llm].timeout_seconds`（默认 180s）
  是**覆盖整条模型回退链的 RPC 总预算**：链子一长（日志里出现过 4 个模型 × 30s × 2 次）
  就会在链路跑完前先被 RPC 超时切断，日志表现为
  `选材分块超时（跳过本块）: [E_TIMEOUT] 请求 cap.call 超时 (180000ms)` ——
  这个降级是有意的（跳过本块、用其余块继续），**选材全块都超时**才降级用时间线末尾。
  治本仍是调大对应 API Provider 的 `timeout`，或换一条稳定的 Provider（插件改不动 Host 配置）。

  **调参口径（真机实测支撑）**：日志显示该链上确实有能成功的慢模型
  （`db-deepseek-v4-flash-ga-260731`：3 次调用 / 平均 **120.4 秒** / 缓存命中 82.79%），
  所以 180s 的总预算**可能比模型链本身还短**。若你经常看到 `cap.call 超时 (180000ms)`：

  ```toml
  [llm]
  timeout_seconds = 300    # 180 → 300：给整条回退链留够时间
  write_retry = 0          # 1 → 0：超时预算是 RPC 总预算，重试会让最坏耗时翻倍
  ```
  单天最坏耗时 = `(1 + write_retry) × timeout_seconds + retry_backoff_seconds`
  （默认 1/180/20 → 380s；上面这组 → 300s）。嫌久就用 `[schedule].catch_up_budget_minutes` 封顶。

- **重试范围补全（v1.4.0，真机实录驱动）**：此前 `write_retry` **只作用于成文阶段**，
  两处缺口在一次真机补跑里同时暴露：
  1. **选材阶段完全没有重试** —— 那一轮"一块因 `[WinError 5] 拒绝访问`、一块因 RPC 超时"
     双双白废，最后只能降级用时间线末尾。现在**单块选材也走重试**（多块刻意不重试：
     块之间本来就是"某块失败就跳过"的降级设计，逐个重试会让整轮成文耗时失控）。
  2. **宿主侧瞬时 I/O 故障被当成不可重试** —— Host 并发写 `llm_error/*.json` 时
     rename `.tmp` → 目标文件被拒：
     ```
     [WinError 5] 拒绝访问。: '…\xxx.json.tmp' -> '…\xxx.json'
     ```
     LLMService 把它当"生成内容时出错"抛出，插件看到
     `选材分块失败（跳过本块）: LLM 调用失败: [WinError 5] 拒绝访问。…`。
     这类失败**与模型无关、且明显瞬时**（下一次 rename 多半就成功），已纳入可重试
     （`WinError 5/32`、`EACCES`、`EPERM`、`EBUSY`、"拒绝访问"、"另一个程序正在使用"…）。
     **格式/语义类失败仍然不重试**（有反向用例守着）。

  旧日记全被留在旧目录里。任何按插件中心规范改过 ID 的人都会撞上同一件事。这一版补两道防御：

  1. **旧 ID 数据目录检测**：启动时若"当前目录为空、而同级目录里有一个含本插件
     `diaries.json` 的目录"，打一条 WARNING 说明原因与手工迁移方法
     （**刻意不自动迁移** —— 自动搬数据可能覆盖更新的内容，风险太高）。
     当前目录已有内容时只记 INFO，不刷 WARNING。
  2. **坏存档不再静默判空**：旧实现
     ```python
     except (json.JSONDecodeError, OSError):
         return {}      # ← 一份存了多天的日记，因一次写入被中断就「全部消失且毫无提示」
     ```
     现在：解析失败**记 ERROR**（含路径/字节数/原因）→ 优先从固定名 `diaries.json.bak`
     恢复 → 再试 `diaries.json.bak.<时间戳>` → 都没有才当空，并明确说明。
     写盘前会自动留一份 `.bak`（固定名，每 60 分钟才刷一次，不会每篇都写两遍）。
     **主文件坏掉时插件不会自动写回**（避免覆盖现场），日志会给出手工恢复命令。

  > 迁移提示：若你换过插件 ID，请把旧目录里的 `diaries.json`（必要时含 `cookies.json` /
  > `continuity.json`）拷进新目录**再**重启。注意新目录里可能已有更新的日期，
  > **不要整个覆盖** —— 可以逐日期比 `generated_at`，只补缺的那些。

- **静默检查跟随取材范围（v1.4.2）**：这是 v1.3.5 收窄默认取材范围时**留下的作用域不一致** ——
  取材只取 `target_chats`，但静默检查（`wait_silent_minutes`）查的是**全库**：

  | 环节 | v1.4.1 及更早 | 作用域 |
  |---|---|---|
  | 取材（进 prompt 的内容） | 只取 `target_chats` | ✅ 白名单 |
  | 静默判断（何时开始写） | **全库任何会话** | ❌ 不一致 |

  后果：你配的是"那个群安静 5 分钟就写"，实际却是"**整个 bot 任何一个会话**都安静
  5 分钟才写"。私聊或别的群一直在聊，就会把当天日记一路推到 `max_wait_hours` 上限才生成，
  而那批消息**根本不会进日记**。

  现在静默检查按取材范围判断：`whitelist` 只看白名单会话（会话解析不出来时复用
  "全库 + 插件内过滤"兜底）；`all` / `blacklist` 保持全库（这两种模式下看全库才对；
  多会话白名单也直接查全库，逐个查纯属浪费）。日志会写清作用域：

  ```
  静默检查（取材范围 group:967779035）：最近 5 分钟内还有 3 条新消息
  静默检查（全库（filter_mode=all））：最近 5 分钟内还有 12 条新消息
  ```

- **日期行不再出现「第二行日期」+ 模型写错日期不再静默（v1.4.3）**：真机 2026-09-28 那篇
  成品里出现了两行日期，天气还互相冲突：

  ```
  2026年9月28日 星期一，多云。
  2026年9月28日 星期一 雨          ← 多出来的第二行日期
  ```

  根因是判据只管「是不是**目标日期**」：`parse_date_line` 遇到"模型写了别的日子"会返回
  `None`，折叠循环一看是 `None` 就 `break` —— 那行日期原样留在正文里，读者看到的第一件事
  就是日记写错了日子。现在判据拆成两个问题：

  | 问题 | 函数 | 用途 |
  |---|---|---|
  | 这一行是不是**目标日期**的日期行？ | `parse_date_line` | 规范化、取天气与行内正文 |
  | 这一行**长得像日期行**吗？ | `_looks_like_date_line` | 折叠"另一天"的日期行 |

  处理方式（**折中方案**，只管成品观感、不假装没发生）：成品里**永远只有一行正确日期**的
  日期行；模型原来写的那一行既不留在正文，也不被悄悄丢掉 —— 它落进存档的
  `model_date_line` 字段，同时打一条日志：

  ```text
  WARNING 模型写的日期行不是 2026-09-28，已去掉并统一为正确日期（原文记入存档 model_date_line）: '2026年9月27日 星期日，晴。'
  ```

  检测（`date_line_overridden`）扫的是**所有行**而不是只看首行，因为真机有两种形态，
  两种都要报出来：

  | 形态 | `ensure_date_line` 的动作 | `model_date_line` |
  |---|---|---|
  | 首行就写错（`2026年9月27日 …` 当首行） | 就地改写成目标日期（行内正文保留） | 那一行 |
  | 首行对、**第二行**写错（真机 09-28 的形态） | 折叠掉第二行 | 被折叠的那一行 |

  > 后一种形态最初**完全没有用例** —— 把折叠逻辑整个退回旧行为时测试仍然全绿
  > （反向验证才发现的假绿）。现在两种形态各有用例，且反向验证确认为 FAIL。

  两点刻意的设计：
  1. **别的日子的天气不采用**（晴/雨属于另一天，拿它当今天的天气就是写错），改用默认值；
     而"只是格式不标准"（漏逗号、短式 `9月28日`、缺句号）时**仍然保留模型观察到的天气** ——
     那是当天，它说的天气算数。
  2. **记录的是"语义替换"而非"格式差异"**：只有日期真的对不上才写 `model_date_line`，
     漏个逗号不会在存档里留噪音（有回归用例守着 `date_line_overridden`）。

- **成文自检三条（v1.4.3，成品文风驱动）**：连续几篇真机成品暴露出同一个结构性毛病，
  prompt 里原有的「禁句式」规则治不了它们（不是句子错，是**段落没内容**）。新增规则 4：

  | 现象 | 真机原文 | 新约束 |
  |---|---|---|
  | **空转动作** | `我问她想好名字了没，她没答` | 动作后面必须跟具体内容（对方说了什么，或我心里怎么想）；只有动作没有内容就是空转，删掉 |
  | **自己复述自己** | `我说不知道，不过最近确实不太一样了。` / `其实我也好奇过自己是什么时候变的` | 同一个意思只写一次；自检办法是「删掉这段最后一句，信息量没变化就删掉它」 |
  | **每段都以感受收尾** | 三段末尾都是"我"的感受 | 全篇最多一段以我的感受收尾，其余落在对方的话、事情的结果、或没解开的地方 |

  两条配套纪律：
  - **反例写进 prompt**：`错误：我问她想好名字了没，她没答（"我问了"素材里没有，"她没答"等于什么都没写成）`
    —— 只说"别空转"模型不知道该躲什么（同 v1.2.7 引号归属那次的修法）。
  - **与事实纪律交叉引用**：规则 7 追加「规则 4a 说的『我问/我说』只能用在**素材真有的互动**上」，
    否则模型会拿"文风自由"给凭空造动作开脱。

  > 边界说明：这三条是**生成侧约束**，不是发布判据。成品里没有"问了但没答"这种可正则判定的
  > 特征（这正是判定它属于 prompt 问题而非校验问题的原因），所以**不会**因此把一篇日记判成不可发布；
  > 回归用例只能守住"约束文本还在 prompt 里"，以及"新约束不改变任何既有判定/规范化契约"。

## 故障排查

**Q: 发了 `/日记` 或 `/问日记`，bot 完全不理我？**

v1.3.4 起权限是 **fail-closed**：`[security].admin_ids` 留空时**谁都不放行**（只放行宿主
bot_console 的本机操作者），非管理员被**静默忽略**（不回复，只留一行日志）。
日志里的判据是这两句之一：

```text
diary 被拒绝：未配置 [security].admin_ids 且 allow_all_users=false（fail-closed）…
diary 命令被静默拒绝（非管理员）
```

修法：把你的 QQ 号填进 `[security].admin_ids = ["你的QQ号"]`（支持 `"qq:123456789"` 写法），
或显式 `[security].allow_all_users = true` 放开所有人（**注意**：`/日记` 会把日记发布到
公开 QQ 空间，且素材默认跨群与私聊合并）。顺带一提，同一会话两次 `/日记` 之间有
`command_cooldown_seconds`（默认 300 秒）冷却，冷却期内会明确回一句「刚写过一篇，N 秒后再试」。

**Q: 日记生成到一半报「LLM 调用失败」？**
看日志里的具体 error。超时可调大 `[llm].timeout_seconds`；确认 `[llm].task_name` 是 Host 模型任务页里存在的任务名。

**Q: 定时任务没跑？**
确认 `[schedule].enabled = true` 且 MaiBot 在设定时间处于运行状态（调度器随插件加载启动，错过当天不补跑）。

**Q: 发布失败，提示登录态失效 / 重取失败？**
`auto_cookie = true` 时插件会自动重取 cookie 再试一次。MaiBot 1.2.x 走 napcat-adapter；**1.3.0 起 adapter 不兼容，请在 NapCat WebUI → 网络配置里开一个 HTTP 服务器**（记下端口和 token，填进 `[qzone].napcat_http_*`），插件会直连 NapCat 拿 cookie，与 MaiBot 版本无关。都没有时才需要手动填 `[qzone]` cookie。

**Q: 提示「拿不到QQ空间cookie」？**
三级来源都没取到：① adapter 未装载/不可用；② NapCat HTTP 未开启或 host/port/token 不对（403 = token 错）；③ 手动兜底没填。按 ①→②→③ 排查，推荐直接用 ②。

**Q: 定时发布后会在群里说话吗？**
默认**不会**（完全静默，只写日志）。想让某个群/私聊收到通知，把 `[schedule].notify_chats = ["group:群号"]` 填上，发布成功/失败都会收到一条短消息。

**Q: 想只给某个群写日记？**

这是**默认行为**（v1.3.5 起）：`[diary].filter_mode = "whitelist"` + `target_chats = ["group:群号"]` 就够了。
反过来，想让它收录全库（跨群+私聊）才需要显式改 `filter_mode = "all"` —— 改之前请先读「数据流向与隐私」。

**Q: 报「没有配置取材范围：filter_mode 为 whitelist（默认）但 target_chats 为空」？**

v1.3.5 起默认不再收录全库素材。按提示填 `[diary].target_chats = ["group:群号"]`（可写多条）
即可；确实想收全库（含私聊）再显式设 `[diary].filter_mode = "all"`。
日志里对应的 WARNING 是 `[diary].filter_mode = whitelist（默认）但 [diary].target_chats 为空：本次不抓取任何消息`。

**Q: 报「取材范围配置问题：target_chats 里有解析不出的目标」（v1.3.6）？**

某个 `target_chats` 条目解析不出聊天流。**最常见的原因不是群号写错，而是这个字段本来是
旧版随手写的、从未生效过**（旧默认 `filter_mode = "all"` 完全不看 `target_chats`），
v1.3.5 把默认改成 `whitelist` 之后它才开始生效。

报错文本里会直接告诉你**宿主返回的结构**（只有类型与键名，不含内容），例如
`返回里没有 stream_id 字段：dict(键=['unexpected_key'])`。两种修法：

1. **换成聊天流 ID**（推荐，绕过解析这一步）：`target_chats` 接受**裸 stream ID**，
   不匹配 `group:` / `private:` 前缀就原样使用。ID 从日志里的 `聊天流ID：xxxxx` 复制，例如：
   ```toml
   [diary]
   filter_mode = "whitelist"
   target_chats = ["05b32a9995a72c59940d9cd171544ac4"]   # 中文虚拟歌手电台FM∞FAST天文台
   ```
2. **回退语义**：`[diary].filter_mode = "all"`（等价于 v1.3.4 及更早的行为，但会把当天
   所有群+私聊合并写进日记再发到公开空间 —— 先读顶部「数据流向与隐私」）。

**Q: 日志里出现「调度器异常退出」（v1.3.5 及更早）？**

v1.3.6 已修：那种情况下调度器会**整个退出、当天剩余时间不再触发**。升级到 v1.3.6 后，
单次生成失败只记一行 `本轮定时触发失败（调度器继续运行，等待下一个时间点）`，循环继续。
如果你现在还在旧版上见过这句，**重启一次 MaiBot** 即可恢复当天调度。

**Q: 定时到点了，群里也没动静、空间里也没发新日记？**
先看日志有没有 `日记成文不可用（…）`。v1.2.6 起，**模型拒答 / 空输出 / 正文不足 20 字**会被发布前语义闸拦下——
本日既不入档也不发布（宁可空一天，也不把「抱歉，作为一个人工智能…」发到公开空间）。常见诱因：
`[llm].task_name` 指到了能力弱或不支持长输出的模型、`[llm].timeout_seconds` 太短导致半截返回。
日志里同时会打出模型原文前 80 字，据此判断是拒答还是截断。

**Q: 为什么昨天没发日记，今天群里却收到一条「补写了…已存档、未发布」？**
v1.2.8 起有「不丢天」两道防线：插件启动时、以及次日 `fallback_time` 时刻，都会扫最近
`catch_up_days` 天，发现缺档就补写。**补写的一律只存档、不发布到QQ空间**
（公开空间不该冒出一条「昨天」的历史说说），想看正文用 `/日记查看 <日期>`。
不想让它补，把 `[schedule].catch_up_enabled` 设为 `false`。

**Q: 想给过去的某一天补一篇日记？**
`/日记 2026-09-20`（管理员）。**非当天的日记只存档、不发布**，回看用 `/日记查看 2026-09-20`，
依据用 `/日记来源 2026-09-20`。未来日期会被直接拦下。

**Q: 到点了但群里正聊得热火朝天，想等大家停下再写？**
设 `[schedule].wait_silent_minutes = 30`（默认 `0` = 关闭）。开启后主触发会先看最近 30 分钟
有没有新消息，有就每 `retry_interval_minutes` 分钟再看一次，直到静默才开始写。
**最多等 `max_wait_hours` 小时**（默认 3），等满照常生成——不丢天优先。
日志会打 `静默检查：最近 30 分钟内还有 N 条新消息` / `等待静默超时…照常生成`。

**Q: 日志里一堆 `任务 'plugin.org.orge-8.better-diary' 的模型 '…' 遇到错误: 网络连接超时`，日记没写成？**
这是 **Host 侧模型 Provider 超时**（日志会写「最大超时时间：30s」），不是插件的问题。
MaiBot 会按模型池依次切换、每个模型重试若干次；**插件侧的 `[llm].timeout_seconds`（默认 180s）
是覆盖整条回退链的 RPC 总预算** —— 链子一长（日志里出现过 4 个模型，4 × 30s × 2 次 = 240s）
就会在链路跑完前先被 RPC 超时切断。三条对策，按性价比排序：

1. **治本**：把 Host 模型配置里对应 API Provider 的 `timeout` 调大，或换一条稳定的 Provider
   （日志末行就是这么建议的）。插件改不动 Host 配置。
2. `[llm].write_retry`（v1.3.2 起默认 1）：成文遇超时会重试，网络抖动那一类往往第二次就过。
3. `[llm].timeout_seconds` 调大（如 300），给整条回退链留够时间；
   代价是单天最坏耗时 = `(1 + write_retry) × timeout_seconds + retry_backoff_seconds`，
   嫌久就用 `[schedule].catch_up_budget_minutes` 给补跑封顶。

另外 v1.3.2 起**补跑按天隔离**：即使某天真的写不出来，也只是那一天缺档，
后面的日期不会再被一起拖死（日志：`补写 <日期> 异常（跳过本日，继续后面几天）`）。

**Q: 日记味道不对？**
先调 `style_extra`（会追加进写作规则）；还不行就改 `persona_override` 完整接管人设描述。

**Q: 启动就失败，报 `No module named 'bd_prompts'`？**
v1.2.1 已修。根因是 Runner **把插件目录当包加载**（目录不在 `sys.path` 上），此时只有相对导入
`from .bd_prompts import ...` 能解析；旧代码用的是平铺导入 `from bd_prompts import ...`，真机必然挂。
修法是双路径导入（相对优先、平铺兜底）+ 补 `__init__.py` 包标记。若你手上是旧版，整目录换 v1.2.1 即可。

> 注意：这类问题**本地冒烟测不出来**——旧的冒烟测试用平铺方式加载，跟真机加载方式不同，
> 所以出现过「门禁全绿但真机启动失败」。v1.2.1 起冒烟测试改为包式加载（显式传
> `submodule_search_locations` 并保证插件目录不在 `sys.path`），与真机一致。

**Q: 报「插件初始化失败」/ 仍提示 `No module named 'bd_prompts'`？**
v1.2.2 已修。**报错信息具有误导性**：真实原因是真机 MaiBot 的 Python 环境**没装 httpx**，
而 `bd_cookie.py` / `bd_qzone.py` 曾在模块级裸 `import httpx`；`plugin.py` 顶层导入它时抛
`ImportError`，被兜底分支误判成「包式加载不可用」，于是回退平铺导入并报出 `bd_prompts` 找不到——
**真因被掩盖了**。

v1.2.2 两处改动根治：

- httpx 改为**可选依赖**（模块内 `try: import httpx` + `HTTPX_AVAILABLE` 标志）。
  没有 httpx 时插件**照常加载**，只有「发布到QQ空间」这一步不可用并给出可读提示；
  日记生成与存档不受影响。
- 导入分支改用 `if __package__:` 精确判断，不再用宽泛的 `except ImportError`
  吞掉下游依赖错误——以后任何依赖问题都会报出真名。

想彻底用上空间发布，二选一：① 在 MaiBot 的 Python 环境里装 httpx（`pip install httpx`）；
② 暂时 `[qzone].enabled = false`，日记仍会正常生成并存档，用 `/日记查看` 取正文。

**Q: 报「插件注册失败 / 插件初始化失败」，且日志里没有本插件任何输出？**

**先试这一步：删掉插件目录里的 `config.toml`，然后完整重启 MaiBot。**

这是本插件真机上**唯一实际发生过**的失败原因，已实测确认。典型场景是
**MaiBot 升级**：`plugin.config_version` 是 **Host 1.2.3 才引入的硬性要求**，而插件目录里那份
`config.toml` 是**旧宿主生成**的、没有这个键。升级后 Runner 一读就判非法：

```text
插件配置版本非法: 插件配置文件缺少 plugin.config_version 版本号，当前版本策略不再兼容无版本配置
```

删掉它，Runner 会按当前配置模型重新生成一份合法配置（只有 `[plugin]` 与你改过的项会重置，
**存档的日记不会丢**——日记在 `data/plugins/` 里，不在插件目录）。
另一种等价做法：在 WebUI 里保存一次该插件的配置。

**为什么日志一片空白？** 因为这个检查发生在 Runner（`runner/runner_main.py::extract_plugin_config_version`）
里，位置在**「配置注入」**阶段——比 `on_load` 更早，此时插件代码一行都还没执行：

```
扫描 plugins/ → 读 _manifest.json（严格校验）→ 校验依赖
   → 导入 plugin.py → create_plugin() → 注入 ctx
   → 配置注入：读 config.toml → 版本检查 ✗   ← 就死在这里
   → on_load()                              ← 这层的失败才报「插件加载失败」
```

> 判据：**「插件初始化失败」≠「插件加载失败」。** 后者才是 `on_load` 抛的异常。
> 看到「初始化失败」就说明还没进你的代码——**不要再去改插件源码**。

**这也意味着插件侧代码无法自救**：拦截点全在宿主，插件能做的只有「换个合法的 config.toml」。
v1.2.2 / v1.2.3 / v1.2.4 做的配置容错（`field_validator` 归一化、覆写 `set_plugin_config`、
逐字段修复）**都不是针对这条路的**——它们仍有价值（覆盖「配置能过版本检查、但字段类型写错」
那类问题），但**治不了上面的场景**。真正有效的动作只有「删 `config.toml` 重生成」。

配置格式参考（Runner 会自动生成，正常不必手写）：

```toml
[plugin]
enabled = true
config_version = "1.0.0"       # ✓ 必须有

[security]
admin_ids = ["123456789"]      # ✓ 标准写法；写成 "123456789" 也接受（v1.2.3 起）
                               #   留空 = 谁都不放行（v1.3.4 起 fail-closed）
allow_all_users = false        # 确需全员可用才改 true
command_cooldown_seconds = 300 # 同一会话两次 /日记 的最小间隔（秒）
```

若确认不是上面这条（即日志里**有**本插件的输出），再去搜这几句：

| 日志关键字 | 含义 |
|---|---|
| `日期行已规范化：模型原文 … → …` | 模型写的日期行格式不标准（漏逗号 / 缺句号 / 短式 / 重复行），已就地统一成「<日期>，<天气>。」——**天气保留模型写的**，不覆盖成默认值 |
| `日记成文不可用（…）` | 模型拒答 / 空输出 / 残句被语义闸拦下，本日不存档、不发布（后面跟着模型原文**字数与开头 80 字**，原文本身不再整体入日志） |
| `引用体检告警：…` | 日记里有「」却没原样引用任何一条素材原话 —— 可能自造原话或引号边界写错。**不阻断**，只留痕（v1.3.4 起只打事件 ID 与条数，不再把聊天原话写进日志；要看原文用 `/日记来源`） |
| `…被拒绝：未配置 [security].admin_ids 且 allow_all_users=false（fail-closed）` | 权限闸拦下（v1.3.4 起 fail-closed）：需要放行就填 `admin_ids`，或显式 `allow_all_users = true` |
| `补写缺档 <日期>` | 不丢天防线发现该日期没有日记，开始补写（**只存档、不发布**） |
| `补跑结束：…` | 一次补跑的汇总（尝试几天、成功几天） |
| `静默检查：最近 N 分钟内还有 M 条新消息` | 静默阈值生效中，还没静默，稍后再看一次（`wait_silent_minutes > 0` 才会出现） |
| `等待静默超时（已等 N 次，上限 H 小时），照常生成` | 等满 `max_wait_hours` 仍未静默，**不丢天优先**直接写 |
| `静默检查失败（按已静默处理，照常生成）` | 消息查询异常，按已静默处理 —— 可选增强绝不挡住当天日记 |
| `选材分块超时（跳过本块）` | 该块选材撞上模型超时；全部块都超时会降级用时间线末尾 |
| `日记成文 第 N/M 次调用超时，S 秒后重试` | 成文遇超时，按 `[llm].write_retry` 重试中 |
| `补写 <日期> 异常（跳过本日，继续后面几天）` | 单天补写抛出异常，已就地收敛；**后面的日期照常补** |
| `补跑已达总预算 N 分钟，剩余日期留给下一轮兜底` | 撞到 `catch_up_budget_minutes` 上限，主动停手 |
| `连续性状态更新失败` | `continuity.json` 写入失败，只影响下一天的「延续感」，不影响本次日记 |
| `插件配置注入失败，已回退…` | 配置能过版本检查、但字段类型有问题，后面跟着真实异常 + traceback |
| `回退配置无法逐字段修复…` | 连逐字段修复都失败，本次用模型默认值运行 |
| `插件配置不可用，已回退默认配置继续加载…` | 配置实例缺失（下游保险生效） |

> 提醒：配置类问题**只有走真实 SDK 的 `set_plugin_config` 才测得出来**。旧冒烟测试的
> `[0c]` 直接调 `BetterDiaryConfig.model_validate`，绕过了版本检查，所以它永远是绿的。
